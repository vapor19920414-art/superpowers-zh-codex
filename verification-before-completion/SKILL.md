# 完成前验证

## 概述

在没有验证的情况下宣称工作完成，这不是高效，而是不诚实。

**核心原则：** 始终用证据支撑结论。

**对这条规则敷衍了事，就等于违背了它的精神。**

## 铁律

```
没有新鲜的验证证据，不许宣称完成
```

如果你在这条消息中没有运行验证命令，就不能声称测试通过。

## 门控函数

```
在宣称任何状态或表达满意之前：

1. 确定：什么命令能证明这个结论？
2. 运行：执行完整命令（重新运行，完整执行）
3. 阅读：完整输出，检查退出码，统计失败数
4. 验证：输出是否支持这个结论？
   - 如果否：用证据说明实际状态
   - 如果是：带证据陈述结论
5. 只有这时：才能做出结论

跳过任何一步 = 说谎，不是验证
```

## 证据新鲜度与增量修改

验证证据只对它实际覆盖的那版产物有效。完成验证后又发生任何代码、配置、计划或依赖变化时：

1. 旧证据对受影响结论自动失效，不得继续引用为“已通过”。
2. 重新读取受影响文件和当前 diff，判断哪些调用链、需求点和验证命令需要重跑。
3. 至少重跑覆盖新增改动及其上下游影响的验证；无法重跑的部分标“待验证”并说明原因。
4. 更新交付摘要，明确旧结论是否仍成立；不得只追加“补了一点修改”而沿用旧完成声明。

## 多 Git 根验证边界

对所有改动文件所在目录执行 `git -C <改动文件所在目录> rev-parse --show-toplevel`，按实际 Git 根分别检查 status、diff 和验证结果。父仓库干净不证明嵌套仓库、submodule 或独立模块干净；每个受影响 Git 根都必须单独给出证据或待验证说明。

## 常见失败模式

| 结论 | 需要 | 不够格 |
|------|------|--------|
| 测试通过 | 测试命令输出：0 failures | 之前的运行结果、"应该会通过" |
| Linter 无报错 | Linter 输出：0 errors | 部分检查、推断 |
| 构建成功 | 构建命令：exit 0 | linter 通过、日志看起来没问题 |
| Bug 已修复 | 测试原始症状：通过 | 代码改了，假设已修复 |
| 回归测试有效 | 红-绿循环已验证 | 测试只通过了一次 |
| 代理已完成 | VCS diff 显示变更 | 代理报告"成功" |
| 需求已满足 | 逐项核对清单 | 测试通过 |

## 红线——停下来

- 使用"应该"、"大概"、"似乎"
- 验证前就表达满意（"太好了！"、"完美！"、"搞定！"等）
- 即将提交/推送/创建 PR 却没有验证
- 信任代理的成功报告
- 依赖部分验证
- 想着"就这一次"
- 累了想赶紧收工
- **任何暗示成功但实际未运行验证的措辞**

## 防止合理化

| 借口 | 现实 |
|------|------|
| "应该能行了" | 运行验证命令 |
| "我有信心" | 信心 ≠ 证据 |
| "就这一次" | 没有例外 |
| "Linter 通过了" | Linter ≠ 编译器 |
| "代理说成功了" | 独立验证 |
| "我累了" | 疲劳 ≠ 借口 |
| "部分检查就够了" | 部分检查什么也证明不了 |
| "换个说法这条规则就不适用了" | 精神大于字面 |

## 关键模式

**测试：**
```
✅ [运行测试命令] [看到：34/34 pass] "全部测试通过"
❌ "应该能通过了" / "看起来对了"
```

**回归测试（仅用户明确要求新增/修改测试时）：**
```
✅ 编写 → 运行（通过）→ 回退修复 → 运行（必须失败）→ 恢复 → 运行（通过）
❌ "我写了回归测试"（没有经过红-绿验证）
```

用户未明确要求新增或修改测试时，不创建回归测试；改用现有测试、构建、静态检查或原问题复现路径验证，并如实说明验证边界。

**构建：**
```
✅ [运行构建] [看到：exit 0] "构建通过"
❌ "Linter 通过了"（linter 不检查编译）
```

**需求：**
```
✅ 重读计划 → 创建核对清单 → 逐项验证 → 报告缺口或完成
❌ "测试通过了，阶段完成"
```

**代理委派：**
```
✅ 代理报告成功 → 检查 VCS diff → 验证变更 → 报告实际状态
❌ 信任代理报告
```

## 为什么这很重要

来自 24 次失败记录：
- 搭档说"我不信你"——信任被破坏
- 未定义的函数被交付——会直接崩溃
- 遗漏需求被交付——功能不完整
- 虚假完成浪费的时间 → 返工 → 重做
- 违反原则："诚实是核心价值。如果你说谎，就会被替换。"

## 何时使用

**以下情况之前必须使用：**
- 任何形式的成功/完成声明
- 任何满意的表达
- 任何关于工作状态的正面陈述
- 提交、创建 PR、标记任务完成
- 进入下一个任务
- 委派给代理

**本规则适用于：**
- 准确措辞
- 同义词和换一种说法
- 暗示成功
- 任何传达完成/正确性的沟通


## 证据回指纪律

每条"通过/完成/已修复"结论必须能回指到**具体证据片段**：

| 结论类型 | 回指要求 |
|---------|---------|
| 测试通过 | 测试命令 + 输出摘要（如"34/34 pass"） |
| 构建成功 | 构建命令 + exit code |
| Bug 已修复 | 复现原症状的测试 + 通过输出 |
| 代码改到位 | 代码 file:line + 关键 diff |
| 需求已满足 | 逐项核对清单 + 每项证据 |

**做不到回指的结论**：只进"待验证"清单，不写进"已完成"。断言无法实证验证时，标 `[未验证-证据不足]`，**不得默认通过**。

这与"门控函数"一致--门控要求运行命令看输出，回指纪律要求把输出片段锚定到每条结论上，让结论可追溯、可复核。

> 本段提炼自 icode-skill `references/adversarial.md`「证据回指纪律」段，原规则：每条 confirmed 结论必须能回指到具体证据片段（计划章节/代码 file:line/日志节点+时间+原文）。

## 需求收敛三视角

宣称"需求已满足"之前，必须从三个独立视角逐条对照，既防需求遗漏，也防重复实现：

| 视角 | 对照基线 | 检查问题 |
|------|---------|---------|
| **A·需求角度** | 用户原始需求（对话/规格/issue 原文） | 用户想要的每一条，最终产物是否满足？ |
| **B·计划角度** | 实现计划/任务清单 | 计划定义的每个功能点，代码是否落地？ |
| **C·必要性角度** | 最终产物与工程现有行为 | 新增功能是否已有等价实现？应复用、补充还是确需新增？ |

**操作步骤：**

1. **拆解需求**：重读用户原始需求，逐条拆解为可验证的需求点
2. **三视角对照**：每个需求点同时从需求、计划和现有实现三个视角给出判定；视角 C 的文本命中必须追到调用链和实际行为

```markdown
| 需求点 | A·需求角度 | B·计划角度 | C·必要性角度 | 收敛判定 |
|--------|------------|------------|----------------|---------|
| <需求 1> | 用户原话 -> 产物满足 ✅ | 计划 §X.Y -> 代码 file:line ✅ | 无等价行为 ✅ | ✅ 收敛 |
| <需求 2> | 边缘 case 未覆盖 ❌ | 计划 §X.Z -> 代码 file:line ✅ | 部分覆盖，边界已说明 | ❌ 追加修复 |
| <需求 3> | 用户需求已存在 | 计划遗漏 ❌ | 现有入口已完整覆盖 | ❌ 改为复用/取消新增 |
```

3. **收敛判定**：三个视角都通过才算收敛；任一未通过 -> 修正计划、改为复用或追加修复任务，不得跳过

**三个视角的区别**：B 检查“计划定义的做了没”，A 检查“用户想要的做了没”，C 检查“做的事情是否本来就已有实现”。三者互不替代。

**与门控函数的关系**：门控函数要求“什么证据能证明结论”，三视角要求“哪些需求点、计划点和必要性需要验证”，把笼统的“需求已满足”拆成可复核的对照表。

> A/B 视角提炼自 icode-skill 原始需求收敛机制；C 视角提炼自 v2.11 `references/necessity_check.md`，均已去除 metadata 和工单状态依赖。

## 底线

**验证没有捷径。**

运行命令。阅读输出。然后才能宣称结果。

这没有商量余地。
