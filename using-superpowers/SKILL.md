## 规则

**在任何响应或操作之前调用相关或被请求的技能**——包括澄清性问题、探索代码库、或查看文件之前。如果调用后发现技能不适合当前情况，你不需要使用它。

**在进入计划模式之前：** 如果你还没有头脑风暴过，先调用头脑风暴技能。

然后宣布"使用 [技能] 来 [目的]"，并严格遵循该技能。如果它有检查清单，为每个条目创建一个待办。

## 技能优先级

当多个技能都适用时，流程技能优先——它们决定处理方式，然后由实现技能（前端设计等）负责执行。头脑风暴和系统化调试是 Superpowers 中最常见的流程技能，但这条规则适用于任何流程技能。

- "让我们构建 X" → 先用 superpowers:brainstorming，再用实现技能。
- "修复这个 bug" → 先用 superpowers:systematic-debugging，再用领域技能。

## 需求文档与设计规格评审路由

当用户要求分析、评审、完善需求文档，或确认设计是否满足落地条件时，**必需子技能：** 使用 `brainstorming` 进行规格收敛。`chinese-documentation` 仅负责最终中文排版，`chinese-code-review` 仅可作为最终审查的表达层，不得替代规格收敛流程。

评审发现必须先分流，再决定是否询问用户：

| 类型 | 处理方式 |
|------|---------|
| 技术确定项 | 通过现有代码、协议或文档查证并自行补齐，不得转交用户裁决；评审仅授权只读时给出明确结论，已授权修改时直接回填文档。 |
| 产品裁决项 | 仅保留确实存在多种产品行为且现有证据无法确定的事项；给出推荐方案和影响，每次只讨论一个。 |
| 外部依赖或后续能力 | 记录前置条件、当前边界和扩展锚点；不影响当前版本时不得阻塞收敛。 |

**不得只列出问题清单后停止，等待用户追问“下一步怎么做”。** 有产品裁决项时，在同一轮评审结论后主动进入第一个裁决项；没有产品裁决项时，根据当前授权继续更新文档或给出明确的落地结论。

## 红线

这些想法意味着停下——你在合理化：

| 想法 | 现实 |
|------|------|
| "这只是一个简单的问题" | 问题就是任务。检查技能。 |
| "我需要先了解更多上下文" | 技能检查在澄清性问题之前。 |
| "让我先探索一下代码库" | 技能告诉你如何探索。先检查。 |
| "我可以快速查一下 git/文件" | 文件缺少对话上下文。检查技能。 |
| "让我先收集信息" | 技能告诉你如何收集信息。 |
| "这不需要正式的技能" | 如果技能存在，就使用它。 |
| "我记得这个技能" | 技能会迭代更新。阅读当前版本。 |
| "这不算一个任务" | 行动 = 任务。检查技能。 |
| "技能太小题大做了" | 简单的事会变复杂。使用它。 |
| "让我先做这一件事" | 在做任何事之前先检查。 |
| "这样做感觉很高效" | 无纪律的行动浪费时间。技能防止这一点。 |
| "我知道那是什么意思" | 知道概念 ≠ 使用技能。调用它。 |


## 执行反偷懒约束

调用技能后，执行过程中禁止以下偷工减料（一经发现，该步骤产出视为不合规）：

| 偷懒行为 | 合规要求 |
|---------|---------|
| 合并产出：把多个独立产物揉进同一文件 | 每个产物独立成文 |
| 跳过子项：技能要求的子项/维度/章节写"略""同上" | 完整覆盖所有子项 |
| 降低轮次：审查/复检轮次未达标就声称"已无新问题" | 达标或有明确收敛判据 |
| 伪代码替代实现：用 `// TODO`/`// ...` 占位代替真实代码 | 落地可运行代码 |
| 审查/验证走过场：结论全是"无问题""通过"无具体证据 | 每条结论附证据回指 |
| 跳过验证就宣称完成：未运行验证命令就声称通过 | 见 verification-before-completion |
| 伪造共识/默认通过：证据不足时默认确认、对抗未收敛时和稀泥 | 证据不足标"待验证"，不伪造确认 |

**总则**：禁止以"省 token/省时间/已大致足够"为由跳过技能定义的子项、轮次和验证。完整完成，不得合并、跳过、降级。

## 工具调用模式规范

解决"每次只发一个工具调用，等结果回来后就停，需要用户手动点继续"的交互问题。**两条硬性规则**：

1. **批量独立调用**：对无依赖、只读或不共享写入目标、且当前工具允许并行的调用，应在同一个回复中批量发出。包括但不限于：
   - 多个独立文件的 Read
   - 多个独立目录的 ls 查询
   - 多个不相关的 grep/ripgrep 搜索
   - 多个互不依赖的 Bash 命令
   - 多个独立子任务用子代理工具并行启动

   **例外**：有副作用、共享资源/写入目标、受速率或并发配额限制，或工具明确要求串行/禁止并行的调用，必须串行执行。

   **判定**：A 的结果影响 B 的执行 -> 串行；A 和 B 互不依赖，且满足上述并行前提 -> 在同一个回复中批量并行发出。

2. **连续执行不等待**：拿到工具结果后，在同一回复中立即继续后续步骤/决策，不等用户主动推进。仅以下情况可以停下来问用户：
   - 需要用户做二元决策（如"复用/新建"）
   - 不可逆操作需用户确认（如删除/覆盖文件）
   - 信息不足以推进（如需要用户补充需求细节）

**违规**：对满足并行前提的独立调用无故拆分发送、每次停下来等用户推进后才继续。
**合规**：对满足并行前提的调用批量发送 + 拿到结果后立即继续。

> 本段提炼自 icode-skill `SKILL.md`「工具调用模式规范」段，泛化去除 icode 专属的 MCP 调用覆盖强制化关联，保留"批量并行 + 连续执行"核心规则。平台中性，Claude Code / Codex CLI 均适用。

## 重要决策记录

重要判断或方案取舍前，先完成结构化分析，但**不得要求输出或暴露模型的内部推理过程**。对用户和后续审查者只保留可复核的决策记录：

- 已确认事实及证据来源
- 仍待验证的假设或限制
- 采用的方案、主要取舍和验证方式

当前平台提供思考类工具时可按需使用；工具不可用不构成阻塞，也不要求用显式“思考块”代替。需要跟踪多步骤工作时使用当前平台的计划/待办工具。

## 中国特色技能路由

> 🇨🇳 **本节是 superpowers-zh 的增量内容，上游 obra/superpowers 没有。**
> 用于把中文场景路由到本 fork 原创的 chinese-* 系列 skill。其余各节均为逐节翻译。

当检测到以下场景时，**必须**优先调用对应的中国特色技能：

| 场景 | 调用技能 |
|------|---------|
| 代码审查且团队使用中文沟通 | **superpowers:chinese-code-review** |
| 使用 Gitee/Coding/极狐 GitLab | **superpowers:chinese-git-workflow** |
| 编写中文技术文档或 README | **superpowers:chinese-documentation** |
| 编写 git commit message（中文项目） | **superpowers:chinese-commit-conventions** |
| 构建 MCP 服务器/工具 | **superpowers:mcp-builder** |

**判断依据：**
- 项目中有中文注释、中文 README、或 .gitee 目录 → 启用中文系列技能
- commit 历史中有中文 → 使用中文提交规范
- 用户用中文交流 → 所有输出使用中文，优先考虑中国特色技能

中国特色技能与翻译技能**叠加使用**，不互斥。例如：做代码审查时，同时使用 requesting-code-review（流程）+ chinese-code-review（风格）。
