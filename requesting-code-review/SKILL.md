# 请求代码审查

派遣代码审查子代理，在问题扩散之前发现它们。审查者获得的是精心组织的评估上下文——绝不是你的会话历史。这样可以让审查者专注于工作成果而非你的思考过程，同时保留你自己的上下文以便继续工作。

**核心原则：** 早审查，勤审查。

## 何时请求审查

**必须审查：**
- 子代理驱动开发中每个任务完成后
- 完成重要功能后
- 合并到 main 之前

**可选但有价值：**
- 卡住时（换个视角）
- 重构之前（建立基线）
- 修复复杂 bug 之后

## 如何请求

**1. 获取 git SHA：**
```bash
BASE_SHA=$(git rev-parse HEAD~1)  # 或 origin/main
HEAD_SHA=$(git rev-parse HEAD)
```

**2. 派遣代码审查子代理：**

使用 Task 工具，指定 `general-purpose` 类型，填写 `code-reviewer.md` 中的模板

**占位符说明：**
- `{DESCRIPTION}` - 你刚完成的内容简要说明
- `{PLAN_OR_REQUIREMENTS}` - 预期功能
- `{BASE_SHA}` - 起始提交
- `{HEAD_SHA}` - 结束提交

**3. 处理反馈：**
- Critical 问题立即修复
- Important 问题在继续之前修复
- Minor 问题记录下来稍后处理
- 如果审查者有误，用技术理由反驳

## 示例

```
[刚完成任务 2：添加验证功能]

你：让我在继续之前请求代码审查。

BASE_SHA=$(git log --oneline | grep "Task 1" | head -1 | awk '{print $1}')
HEAD_SHA=$(git rev-parse HEAD)

[派遣代码审查子代理]
  DESCRIPTION: 添加了 verifyIndex() 和 repairIndex()，支持 4 种问题类型
  PLAN_OR_REQUIREMENTS: docs/superpowers/plans/deployment-plan.md 中的任务 2
  BASE_SHA: a7981ec
  HEAD_SHA: 3df7661

[子代理返回]:
  优点：架构清晰，测试真实
  问题：
    Important：缺少进度指示器
    Minor：报告间隔使用了魔法数字 (100)
  评估：可以继续

你：[修复进度指示器]
[继续任务 3]
```

## 与工作流的集成

**子代理驱动开发：**
- 每个任务完成后审查
- 在问题叠加之前发现它们
- 修复后再进入下一个任务

**执行计划：**
- 每个任务完成后或在自然 checkpoint 审查
- 获取反馈，应用，继续

**临时开发：**
- 合并前审查
- 卡住时审查


## 对抗验证增强（可选）

单一审查者存在确认偏误风险（自己委托的审查者，容易顺着你的预期给意见）。对**判断性结论**（"这个设计合理吗""风险够不够"这类无铁证的判断），可追加对抗验证：

**spawn 3 个独立质疑者（必须独立 spawn，不得主代理自演）：**

| 质疑者 | 攻击点 |
|--------|--------|
| 证据质疑者 | 引用的证据真在代码/日志里吗？是否断章取义？ |
| 替代解释者 | 有没有别的原因能解释？（必须提 ≥1 个竞争假设） |
| 充分性质疑者 | 现有证据够不够定论？还缺什么？ |

**裁决优先级（按顺序判定，命中即定）：**
1. `refuted`：≥2 质疑者判推翻，或替代解释者给出被证据支撑的竞争解释 -> 撤销
2. `needs_more_evidence`：充分性质疑者判证据不足 -> 降级待验证（一票否决）
3. `confirmed`：≥2 质疑者判成立 -> 保留
4. 兜底：三态分裂/未收敛 -> 降级待验证，如实记录"对抗未收敛"

**诚实降级（硬约束）：** 对抗未收敛时**不得和稀泥默认 confirmed**，必须降级为 `needs_more_evidence` 并如实记录。宁可承认"这条没验成"，也不伪造共识。

**主代理实证 ≠ 自演：** 主代理用 Read/Grep 查到的代码/日志铁证（如"某函数签名确实是 X"）属事实核查，可直接 confirmed 无需对抗。**必须独立对抗的**是判断性结论--无铁证、依赖独立视角的判断，主代理自演无效。

**显式等待 + 超时（防"未等子代理返回就降级"）：** spawn 质疑者后必须等 verdict 返回才能进入裁决。超时阈值默认 120 秒。超时触发重试 1 次（换措辞，并仅在当前接口实际支持时调整执行配置）；二次仍超时或无 verdict -> 进入失败处理链路。区分四种状态：

| 状态 | 含义 |
|------|------|
| `sync_ok` | 同步等 verdict，120s 内返回 |
| `timeout_retry_used` | 触发 1 次超时重试 |
| `still_failed_after_retry` | 重试后仍超时/无 verdict |
| `env_no_spawn` | 环境结构性无 spawn 工具（见下方降级路径） |

**子代理失败处理（重试 2 次，绝不自演）：** 质疑者返回空/截断/无裁决时：
1. **第 1 次重试**：换措辞（强化"先给裁决再给依据"），子代理类型不变
2. **第 2 次重试**：在当前接口实际支持的范围内更换执行配置（如可用模型或推理强度）；接口不支持时保持配置不变，仅更换措辞后再 spawn 一次
3. **重试 2 次仍失败** -> 诚实降级为 `[未验证-子代理对抗失败]`，计入待验证清单，**绝不改由主代理自演裁决**（自演=既当运动员又当裁判，确认偏误倾向确认自己结论）

**环境无 spawn 工具的降级路径：** 当当前会话结构性无子代理 spawn 能力（工具未暴露、调用明确返回不支持，或会话类型不支持子代理）时，**不重试、不自演**，走以下降级路径：

1. **诚实降级**：标 `[未验证-环境无spawn工具]`，**非** `[未验证-子代理对抗失败]`（区分结构性不可用 vs 临时失败）
2. **不重试**：环境无工具，重试无意义
3. **主代理代行（有条件，不同于自演）**：环境结构性无 spawn 工具是**唯一允许**主代理代行的场景。代行时必须：
   - 三个视角的推理各自独立（不得"证据也没问题、替代也没发现竞争解释、充分性也够了"这种一致假共识）
   - 证据质疑者：核对至少 3 条证据指针的原文（Read 实证）
   - 替代解释者：提至少 1 个竞争解释
   - 充分性质疑者：列出至少 1 条"还缺的证据"
   - 标 `[未验证-环境无spawn工具]` 诚实告知用户
4. **有 spawn 工具时硬禁止代行**：即使部分子代理未返回（如 1/3 返回、2/3 超时），未返回的应按失败处理链路降级，**不得"补齐"为主代理代行**

**Codex CLI 判定方法**：以当前会话是否实际暴露且可调用 `spawn_agent` 为准；配置文件只能作为排障线索，不能单独判定环境无 spawn 工具。

> 本段提炼自 icode-skill `references/adversarial.md`「显式等待+超时机制」「子代理失败处理」「环境无 spawn 工具场景」三段，泛化去除 icode 专属的 `task_timeout_seconds` metadata 字段、`no_spawn_env` flag、产物文件标记要求，保留四态枚举 + 重试 2 次 + 环境无 spawn 降级核心规则。Codex 以当前会话实际工具能力判定。

## 多层审查增强（可选）

单层审查（一个 reviewer 看完 diff 给意见）容易遗漏深层问题。对重要变更，可使用三阶段递进审查，每阶段有独立目标，逐层加深：

### 第 1 层·逆推（Reverse）

**不看计划**，只读最终代码，从代码逆推"它在实现什么需求"，再与实际计划/需求对比。

- 目标：发现"代码做了计划没写的、计划写了代码没做的"差异
- 操作：读代码 -> 逆推需求规格 -> 与计划逐项对比 -> 列出差异清单
- 价值：不受计划锚定，纯粹从产物倒推，能发现计划盲区

### 第 2 层·固定维度（Fixed）

对照计划 + 最新代码，逐项覆盖以下固定审查维度：

| # | 维度 | 检查问题 |
|---|------|---------|
| 1 | 逻辑合理性 | 代码逻辑是否自洽？流程是否闭环？ |
| 2 | 流程完整性 | 正常路径 + 异常路径 + 边界路径是否全覆盖？ |
| 3 | 场景覆盖度 | 空入参/超长输入/并发/重入/资源耗尽等场景是否处理？ |
| 4 | 风险遗漏 | 是否有未识别的风险（安全/性能/兼容性/数据丢失）？ |
| 5 | 落地可行性 | 接口签名/数据结构/依赖关系是否可编译可运行？ |
| 6 | 现有实现对照 | 是否复用了既有模式？是否与周围代码风格一致？ |
| 7 | 跨文件一致性 | 接口变更是否全链路同步？上下游数据结构是否对齐？ |

### 第 3 层·自由探索（Free）

不受固定维度限制，从以下角度自由审查，重点是前两层没覆盖的盲区：

- 安全漏洞 / 并发与重入安全 / 资源与内存管理
- 性能热点 / 可测试性 / 可维护性
- 编译器/构建兼容 / 跨平台与移植 / API/ABI 兼容
- 注释完备性与一致性 / 日志覆盖

### 使用建议

- **小变更**：仅第 1 层（逆推）即可--快速发现"做了没做对"
- **中等变更**：第 1 + 2 层--逆推 + 固定维度覆盖
- **重要变更**（合并到 main / 核心模块改动）：三层全跑
- 三层发现的问题统一汇总，按 Critical/Important/Minor 分级处理

> 本段提炼自 icode-skill `steps/05_deepcheck.md`「三阶段递进复检」机制（Reverse -> Fixed -> Free），原规则在 icode 步骤 5 执行，依赖 03_plan_final.md / metadata 字段。此处泛化去除 icode 专属概念，保留三阶段递进结构与核心维度。

## 红线

**绝不要：**
- 因为"很简单"就跳过审查
- 忽略 Critical 问题
- 带着未修复的 Important 问题继续推进
- 对合理的技术反馈进行争辩

**如果审查者有误：**
- 用技术理由反驳
- 展示证明其可行的代码/测试
- 要求澄清
