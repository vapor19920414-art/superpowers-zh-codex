# TB 日志分析、报告迭代与修复衔接

本参考约束附件下载后的上下文使用，以及分析报告到代码修复的状态转换。核心原则：**材料落盘不代表可以全量加载；报告获认可不代表可以自动发布或部署。**

## 1. 建立分析基线

1. 读取 `{ID}_meta.json`，确认项目、缺陷 ID、标题、描述、评论、更新时间和附件摘要。
2. 若同目录已有报告，继续使用同一份 `{ID}_分析报告.md`；重新拉取 TB 元信息并比较更新时间、评论和附件变化，不另起报告。
3. 若用户要求 `worktree`，使用 `using-git-worktrees` 在代码仓建立或识别隔离工作区，并把代码仓、worktree 路径、分支和基线提交写入报告。worktree 只存代码，报告保留在 TB 缺陷目录。
4. 执行只读基线检查。分析阶段不得修改业务代码；项目构建基线可在真正进入修复前执行，避免仅为缺证据的工单消耗大量构建资源。

报告头部必须记录：

```markdown
- 分析状态：证据不足 / 分析中 / 待用户复核 / 已认可待修复 / 修复中 / 已验证
- 代码仓：<绝对路径或未提供>
- 分析工作区：<worktree 绝对路径或未创建>
- 工作区归属：未创建 / 本任务创建 / 既有用户工作区
- 分支 / 基线提交：<值或未创建>
- 现场运行版本：<节点/模块 -> 版本或 Git Hash + 证据来源；无证据写 unknown>
- 分析时版本：<代码仓 -> 首次解释现场代码时的 HEAD；后续变化追加到增量更新记录>
- 修复验证版本：<代码仓 -> 实际部署并验证的版本；未部署或未验证时明确标注>
- 业务子仓工作区：<相对路径 -> worktree/分支；分析阶段通常为待定>
- 修复模式：未选择 / 完整 / 快速
- TB 最近更新时间：<时间>
```

现场运行、分析时和修复验证版本不得混用。分析时版本首次使用代码解释现场时即冻结；后续 HEAD 变化只追加到“增量更新记录”，不得覆盖原分析基线。日志分析前先从启动日志、版本文件、固件清单或二进制版本输出提取现场版本；TB 评论中的版本只作待验证线索。Git Hash 必须同时满足“位于版本语义附近”和“能在对应模块仓唯一解析”，多仓项目按模块分别记录。

现场 Hash 可解析时，只用 `git show <hash>:<path>` 等只读命令核对现场代码，并与当前 HEAD 做相关文件的演进对照；禁止为读历史版本执行 checkout、switch、reset 或 stash。Hash 本地不可解析时不得自动 fetch，标记 `unknown/unresolved` 并降低代码机制结论置信度。当前 HEAD 已包含修复时优先定位并验证已有修复，不重复实现；当前 HEAD 的后续回归不能反向解释更早现场。只有实际部署和覆盖相应场景后，才能填写修复验证版本并标记“已验证”。

## 2. 附件只做清单，不做全文加载

先清单化，再按假设取证：

- 普通文件：记录相对路径、类型、大小和修改时间；使用 `rg --files`、`stat`、`file`、`du`，不要递归读取内容。
- 压缩包：先用 `unzip -l`、`tar -tf` 或同类只列成员；按节点、时间和文件名筛选后再选择性解压。禁止先把整个归档内容灌入上下文。
- 日志：先围绕标题中的时间、动作、错误码、节点和状态做计数或窄范围检索，再用 `sed -n`、`head`、`tail` 读取通常 100–300 行的连续片段。输出可能超过 1000 行时先用 Headroom；不可用时继续过滤、分段。
- 视频：始终遵守 SKILL.md 的二次确认门禁。下载过、本地已有或用户说“分析附件”都不等于允许读取视频流。

每轮读取必须能回答一个问题：它将证实或排除哪个候选机制？如果不能回答，就不要读取。扩大节点、时间窗或文件范围时，在报告的“增量更新”中写明原因。

## 3. 证据驱动分析

使用 `systematic-debugging`，按以下顺序闭环：

1. 从缺陷描述提取预期、实际、操作步骤、时间点、版本和设备条件；缺失项写入证据缺口。
2. 建立跨模块时间线，区分请求、准入/状态机、命令发送、传输/ACK、板端反馈和物理结果。
3. 每个候选根因必须列出支持证据、反证、尚缺证据和置信度；代码路径只能解释机制，不能替代现场日志。
4. 证据不足时报告状态必须是“证据不足”，列出下一轮最小材料请求；不得用代码猜测补齐现场事实。

## 4. 报告格式与增量更新

报告至少包含：

1. `0. 结论摘要与分析状态`
2. `1. 缺陷契约与证据清单`
3. `2. 事件时间线与原始证据`（精确到文件和行号/时间戳）
4. `3. 跨模块链路与候选根因`
5. `4. 已证实、推测与证据缺口`
6. `5. 修复方案、影响范围与风险`
7. `6. 验证边界与建议步骤`
8. `7. 工作区绑定与下一门禁`
9. `8. 增量更新记录`

用户追问时不创建第二份报告：

- 质疑根因：只重跑被质疑的证据分支，更新对应结论、置信度和方案。
- 修正事实/范围：同步修正摘要、时间线和影响范围，并在“增量更新记录”写时间和原因。
- TB 出现新评论或附件：重新拉取并比较元信息，只分析新增或变化部分。
- 补充视频授权：仅分析用户确认的时间点或范围，并把授权范围写入报告。

报告状态为“待用户复核”后停止代码修改。只有用户明确表示报告无问题并要求修复，才能继续。

## 5. 复用 worktree 进入修复

进入修复前先从报告读取工作区绑定，并用 `git worktree list`、`git status --short --branch` 和 `git rev-parse HEAD` 校验路径、分支、仓库及基线。绑定有效就原地复用；失效或冲突时说明具体问题并等待用户决定，禁止静默新建第二个顶层 worktree。

RL2601 这类“顶层管理仓 + 多个被忽略的独立业务仓”需要额外门禁：顶层 worktree 不会自动包含 `hmi_note`、`broker`、`mission_controller`、`mcu_communication` 等业务仓。分析阶段先确定真实影响模块，不预建全部子仓；报告获认可、进入修复前，必须为每个实际受影响业务仓创建独立 worktree，落到顶层 worktree 的同名相对路径，并把路径/分支写回报告。禁止软链到主工作区业务仓，也禁止在原业务仓直接修改。未确定影响模块时保持“待定”，不得用空的顶层 worktree 宣称具备可构建性。

分流规则：

| 模式 | 适用条件 | 后续技能 |
|------|----------|----------|
| 完整 | 跨模块/跨仓；协议、状态机或安全相关；候选根因未唯一；预计超过 5 个相关文件 | `writing-plans` 后按批准计划实施 |
| 快速 | 单模块；根因和边界明确；有同类实现可复用；不改协议/架构/安全逻辑；预计不超过 5 个相关文件 | 直接做最小修改并按项目规则验证 |

不确定时使用完整模式。无论哪种模式，修复前都要复核真实入口、调用链、上下游和同类实现；只改最小范围。未获授权时不新增单测、不 commit、不 push、不部署、不改 TB 状态、不发 TB 评论。

### 5.1 worktree 收尾

交付最终结论、修复已进入目标仓库、修复被撤回或确认无需修复时，都要审计报告绑定的 worktree：

1. 只处理“工作区归属=本任务创建”的精确路径和分支；既有用户工作区及归属不明对象只报告，不清理。RL2601 多仓结构按报告中的业务子仓清单从内到外处理，不能用顶层 `git status` 代替子仓检查。
2. 对每个顶层/业务子仓分别核对工作树干净、分支相对目标分支没有独有提交，并确认预期成果已进入目标仓库或已明确废止。
3. 三项都成立时，先清理业务子仓，再清理顶层 worktree；每层都用 `git worktree remove <精确路径>` 和非强制 `git branch -d <精确分支>`。任一项不成立则保留并说明未提交文件、独有提交或归属缺口。
4. 清理后重新执行 `git worktree list` 和精确分支查询，确认没有任务残留。禁止常规执行全局 `git worktree prune`，禁止 `-D`、`--force` 或文件系统递归删除。

## 6. TB 评论回写边界

本 skill 当前只生成草稿。评论回写不是报告生成的“收尾步骤”，因为它会改变外部协作状态，而且当前 POST 路径、CSRF/鉴权字段、正文格式、幂等和失败重试语义未验证。

若未来实现回写，必须单独设计并验证：

1. 先抓包确认接口和最小 payload，并在测试缺陷上验证。
2. 默认 dry-run，展示目标项目、缺陷 ID 和评论全文。
3. 每次发布前取得用户明确确认；报告更新、修复完成或草稿生成都不得自动触发。
4. 禁止隐式重试，成功后记录服务端返回的评论 ID 和时间，便于审计及去重。
